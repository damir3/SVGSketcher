# Rust geometry kernel

The editor routes intersections between segments, circles, ellipses and cubic Bezier segments through a versioned `GeometryKernel` boundary. Circular and elliptical arcs use the same kernel calculations, with the existing arc-span filtering and point deduplication in the TypeScript adapter. Composite splines are expanded into cubic pairs in their original traversal order; their intersection calculations run in the active kernel.

In WASM mode, the numerical constraint-solving loop also runs in Rust: sparse Jacobian rows and normal equations, sparse LU decomposition with partial pivoting, Levenberg–Marquardt damping, projected lower bounds and sparse nullspace analysis. Rust also evaluates residuals and Jacobians for 32 built-in constraint classes: fixed, drag point, coincident, concentric, horizontal, vertical, radius, equal radius, distance, equal length, midpoint, point on circle, point on line, parallel, perpendicular, collinear, angle, tangent line/circle, tangent circle/circle, ellipse axis, point on ellipse, circular arc endpoints, elliptical arc endpoints, point-to-line distance, symmetry, circular pattern, rectangular pattern, offset, origin distance, line-to-axis distance, point on spline and solve-time automatic spline handles. Customized constraints and unusual nonclamped B-spline knot vectors retain batched TypeScript evaluation. The spline constraints construct and project curves entirely in Rust. Standalone construction, evaluation, projection and cubic splitting used by rendering, snapping and editing now use the selected kernel too. Parameter ownership, document operations, SVG formatting and viewport transforms remain in TypeScript. The original spline arithmetic is retained in `src/math/splineReference.ts` as an independent reference.

`getCurveIntersections` batches primitive pairs to reduce JS/WASM calls. A query containing composite splines submits all cubic combinations in the same batch, then filters spans and deduplicates the combined results. In WASM mode, region construction runs entirely in Rust through one `find_regions_packed` call: conservative bounds, exact intersections, cuts and spline projection, curve sampling, graph construction, iterative bridge removal, face traversal, nested holes and numeric boundary commands. Cubics use control hull bounds and arcs use full conics, padded for the existing contact tolerances. Segment/ellipse pairs retain exact evaluation because their discriminant tolerance is not a fixed world-space distance. The inexpensive bounds scan remains O(n²). Kernel data contains world-space coordinates and call-local identity tags, without DOM, viewport or document dependencies.

`src/math/regionsReference.ts` retains the pre-native TypeScript algorithm, including the bounds filter. The public region API selects `GeometryKernel.findRegions` when available and otherwise uses this reference. Vec2 reconstruction and SVG string formatting remain in TypeScript; API 22 also routes point-in-region queries through Rust. Native failures propagate rather than silently running a second algorithm. The Rust graph uses numeric nodes and edges; insertion-order vectors preserve traversal order, while hash maps serve only lookup. Quantized keys retain JavaScript rounding at negative halves and the original neighboring-key merge behavior. The 10,000-edge face guard, sampling counts, thresholds, source-edge replacement and direct-child hole rules are preserved.

## Build and run

Install Rust 1.88 or later using your usual toolchain setup, then install the target and the CLI matching the pinned Rust dependency:

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.105 --locked
npm run build:kernel
npm run dev
```

For a production WASM build:

```sh
npm run build:wasm
npm run preview
```

`npm run dev` and `npm run build` load WASM by default. Build the kernel first, or use `build:wasm` to rebuild everything together. `VITE_GEOMETRY_KERNEL=typescript npm run dev` explicitly selects the partial reference backend; spline self-intersections and workflows that depend on them require WASM. WASM initialization completes before the editor starts. A loading, initialization or API-version failure leaves the TypeScript backend active and logs the cause to the browser console.

`WASM_BINDGEN=/path/to/wasm-bindgen` can select a CLI outside `PATH`. Generated bindings and the binary go into ignored `public/kernel/`; Vite copies them into the production build. Commit `Cargo.lock`, not the generated files. A deployment that builds only the browser bundle must also generate the kernel assets to use the default WASM backend.

## Boundary and next steps

- `crates/sketcher-core` contains native-testable geometry without JavaScript dependencies.
- `crates/sketcher-wasm` validates and decodes numeric buffers and exports API version 32 through `wasm-bindgen`. Older binaries are rejected before use; rebuild the kernel after updating the source.
- `src/kernel` contains the shared contract, TypeScript backend, WASM adapter and browser initialization.
- Each input curve occupies nine `f64` slots: segment `[0, x1, y1, x2, y2, 0, 0, 0, 0]`, circle `[1, cx, cy, radius, 0, 0, 0, 0, 0]`, ellipse `[2, cx, cy, majorX, majorY, minorX, minorY, 0, 0]`, cubic `[3, x0, y0, x1, y1, x2, y2, x3, y3]`. Every input pair produces `[count, x, y, ...]`, including a count of zero for an empty result. Inputs must contain finite coordinates and nonnegative radii.
- Candidate ordering and existing tolerances are preserved. Arc filtering precedes deduplication so a discarded candidate cannot hide a valid arc contact.

The sampled ellipse/conic root finder retains its existing 128 intervals, 28 bisection steps, tolerances and candidate ordering. This migration does not redesign tangency detection or coincident-ellipse handling. Candidates are filtered by arc span before deduplication, so the packed result allows up to 128 raw candidates for ellipse pairs, including degenerate coincidence cases.

Cubic/conic and cubic/segment calculations retain 16 sampling intervals, 28 bisection steps and the additional near-root check at the final sample. Cubic/cubic calculations retain bounding-box subdivision, depth 15, four Newton refinement steps, the cap of 16 candidate contacts and per-pair deduplication at 1e-3. Composite spline results are subsequently deduplicated at 1e-4 after arc-span filtering. The packed protocol allows up to 17 candidates for a pair containing a cubic.

## Numerical solver boundary

`NumericalSolver.solve` dispatches to the selected kernel's optional `solveSystem`; if absent, it runs the TypeScript solver. Both implementations use sparse rows, duplicate-entry merging, sparse normal equations/LU/nullspace analysis and cached linearization across rejected LM steps. The release profile uses `opt-level = 3`. Fully native systems assemble sparse Jacobians directly through `Program.evaluate_sparse`; mixed JS/native systems retain the dense numeric callback buffer before sparse assembly. `src/solver/kernelAdapter.ts` prepares free parameter indices, hard constraints, stiffness and lower bounds, and converts the result to existing parameter IDs and statuses. `src/solver/nativeConstraints.ts` compiles supported constraints once per solve. Custom subclasses or overridden formula methods retain TypeScript evaluation. The staged radius policy, spline-handle preparation and drag constraints in `SketchDocument.solve` retain their existing behavior.

`solve_system` receives the current free values, stiffness, lower bounds, settings `[equations, hardEquations, skipDoF, maxIterations, tolerance, initialLambda, lambdaFactor, minLambda, maxLambda]`, and packed native constraints. Each native record is `[kind, allRow, hardRowOrMinusOne, weight, a, b, refCount, ...[freeIndexOrMinusOne, constantValue]]`. A negative parameter index denotes a fixed or missing parameter. Rust validates tags, arities, variants, finite constants, parameter indices and non-overlapping equation rows before solving.

The curved constraints add the following tags. Each point below occupies two references (x, y); angle orientation factors are constant references with index -1.

| Kind | References | a | b |
| --- | --- | --- | --- |
| 14: angle | line endpoints (four points), s1, s2, sign | target degrees | axis scaling: 0 neither, 1 first, 2 second |
| 15: line/circle tangency | center, line endpoints, radius | initial side | unused |
| 16: circle/circle tangency | centers, radii | target: 0 sum, 1 first minus second, 2 second minus first | unused |
| 17: point on ellipse | center, major-axis point, minor-axis point, point | unused | unused |
| 18: elliptical arc endpoints | center, major-axis point, minor-axis point, start, end | unused | unused |
| 19: circular arc endpoints | center, start, end, radius | unused | unused |
| 20: point-to-line distance | point, line endpoints | target distance | side |

Shared-point circle tangency reuses kind 10 (point on line through the centers). Ellipse axis perpendicularity reuses kind 12 with an aliased center reference. These preserve the original numerical Jacobians, including perturbing every reference to a shared parameter together. Circular arc endpoints retain their analytic Jacobians.

`src/solver/nativePatterns.ts` expands composite constraints into multiple records in their original equation order. Suppressed copies produce no records; pattern radius pairs reuse kind 5 with pattern radius first. Each record carries both its full-system row and its hard-system row, so empty, soft and mixed JS/native constraints preserve their offsets. If any record cannot be compiled, the entire constraint retains JS evaluation. Native record buffers are appended without spreading them into JavaScript function arguments, including a single variable-size spline record. A 10,000-point packing test checks this limit without attempting a dense solve of that size.

| Kind | References | a | b |
| --- | --- | --- | --- |
| 21: symmetry | point 1, point 2, line endpoints | 0 line, 1 origin | unused |
| 22: circular pattern point | center, source, copy, constant copy index, constant quantity | total degrees | 0 full, 1 partial, 2 symmetric |
| 23: rectangular pattern point | source, copy, line 1 endpoints, line 2 endpoints, constant i, j, direction 1, direction 2, line 1 present, line 2 present | distance 1 | distance 2 |
| 24: offset line endpoint | child endpoint, original line endpoints | distance | side |
| 25: offset circle | child center, original center, child radius, original radius | distance | side |
| 26: offset spline point | child point, constant base point, constant normal, constant side | distance | unused |

Rectangular direction flags are 0 for one direction and 1 for symmetric; presence flags are 0/1. Rust retains the circular quantity rounding, signed copy distributions, rectangular fallback directions at length <= 1e-6, analytic pattern derivatives and the original unfiltered point coefficients. Offset line residuals retain the left-hand sign, 1e-9 length floor and 1e-6 forward differences. All offset Jacobians intentionally drive only child parameters, including the original alias behavior, so master geometry remains unchanged unless another constraint moves it. Spline offsets use stored base positions and normals; this does not migrate spline construction or projection.

Origin and axis constraints use two additional records:

| Kind | References | a | b |
| --- | --- | --- | --- |
| 27: origin distance | point x, point y, constant side | target distance (unused for coincidence) | 0 radial, 1 horizontal, 2 vertical, 3 coincidence |
| 28: line-to-axis distance | selected coordinate of endpoint 1, selected coordinate of endpoint 2, constant side | target distance (unused for collinearity) | 0 distance, 1 collinear |

Kind 27 produces two equations for coincidence and one otherwise; kind 28 always produces two, even for shared endpoints. The compiler selects y coordinates for distance to the X-axis and x coordinates for distance to the Y-axis. These refer to the world origin and axes, independently of similarly named map parameters. The analytic Jacobians retain the 1e-7 radial length floor, division-then-weight operation order and 1e-12 coefficient cutoff. Zero-distance horizontal/vertical equations and coincidence ignore the side; collinear equations ignore both side and distance. Unspecified point orientation retains radial behavior.

Spline records are variable-size and validated before indexing:

| Kind | References | a | b | Equations |
| --- | --- | --- | --- | --- |
| 29: point on spline | target x/y, N curve points; fit tail: N blocks `[constant enabled, h1x, h1y, h2x, h2y]`; control tail: zero or N+4 constant knots | 0 fit, 1 control | N | 1 |
| 30: automatic handles | N fit points, H blocks `[constant fit index, child1x, child1y, child2x, child2y]` | N | H | 4H |

`src/solver/nativeSplines.ts` compiles these records; `crates/sketcher-core/src/constraints/splines.rs` evaluates them. Cubic B-splines preserve linear/quadratic degree elevation and Boehm knot insertion. Fit curves preserve the natural handle formula, 1e-4 closed-seam test, 1e-6 direction threshold, curvature clamp and explicit-handle overrides. Valid clamped nondecreasing explicit knot vectors run natively; other full-length vectors retain JS evaluation. Short knot vectors retain uniform-knot behavior, and knots on curves with fewer than five points remain unused.

Projection retains 12 sample steps per segment, 10 refinement iterations with constants 0.382/0.618, strict comparisons, normalized segment indexing and the 1e-7 tangent-length floor. Its scaled two-coordinate norm matches the captured TS behavior on retraced curves, where one rounding bit can select a different equally close branch. The point-on-spline residual remains signed distance along the projected normal, including the reference behavior beyond endpoints. Its Jacobian uses the existing 1e-5 forward differences and relevance metadata.

Automatic handles retain direct child coefficients plus numerical fit-point derivatives in fit-point insertion order, including the original double contribution when a fit parameter aliases a child. This class ignores its weight in both implementations and remains a solve-time constraint, without changing document serialization. Customized private natural-handle helpers retain JS evaluation.

The `spline_geometry(points, handles, knots, settings)` WASM export serves the editor and independent verification. Settings are `[mode, targetX, targetY, parameter]`; mode 0 returns natural handle coordinates (four slots per point), mode 1 fit cubics, mode 2 control cubics (eight slots per cubic). Mode 3 retains the combined verification query `[parameter, distance, projectedX, projectedY, tangentX, tangentY, sampleX, sampleY]`. Modes 4/5 evaluate normalized position/tangent and return two coordinates. Modes 6/7 evaluate a single cubic/derivative at an unclamped parameter; mode 8 splits one cubic into two (16 coordinates). Mode 9 projects and returns only `[parameter, distance, projectedX, projectedY]`. Scalar evaluation and tangent calls do not run the projection search.

`GeometryKernel.spline` exposes these operations as typed points, cubics, handle pairs and projections. `src/kernel/splineWasm.ts` validates output counts, finite coordinates and projection bounds before returning geometry. Unusual knot vectors and non-finite legacy arguments retain reference behavior. The public `src/math/spline.ts` API still returns `Vec2` instances and preserves shared split endpoints, B-spline joins, empty-curve projection identity and unmodified input data. Its higher-level split/trim/interval functions compose native cubic splits; SVG string generation and viewport transforms remain in TS. The default TS path calls the reference functions directly without repacking vectors. JS constraint formulas import the reference module directly so that they remain independent of the active geometry backend.

`kernelSplineEditing.json` adds 160 pre-routing split, trim and interval snapshots, including clamped and extrapolated parameters. The routing tests verify reference-file identity, vector semantics, every native operation mode and corrupt-result rejection. The existing spline, snapping, region, history and serialization tests now exercise the public routed API with WASM as well as the optimized sparse solver.

Systems entirely covered by native formulas need only accepted-state commit callbacks. For mixed systems, Rust requests one callback per phase that has uncovered rows; TypeScript fills only those rows in the full-sized buffer, then Rust fills native rows:

| Mode | Response |
| --- | --- |
| 0 | All residuals |
| 1 | All residuals followed by a dense row-major Jacobian |
| 2 | Hard-constraint residuals |
| 3 | Hard-constraint Jacobian |
| 4 | Commit the accepted parameter state; return an empty array |

Evaluation inputs and outputs are copied numeric buffers. Rust retains the authoritative trial state during a solve, so callback re-entry or WASM memory growth cannot invalidate a JavaScript view. The result is `[status, iterations, initialError, finalError, DoF, fixedCount, ...values, ...fixedIndices]`, with status tags 0 (converged), 1 (under-constrained), 2 (over-constrained). API compatibility and result shapes are checked before the result is exposed to the model. Exceptions propagate instead of silently running a second solver after partial commits.

Native Jacobians retain the original analytic derivatives, forward/central finite differences, step sizes, derivative cutoffs and accumulation of shared parameter references. The `evaluate_constraints` export evaluates native rows independently for parity tests; its settings are `[equations, hardEquations, mode]` using the same modes above.

The [performance suite](../benchmarks/README.md) now provides six deterministic large scenes, Node solver/region measurements and a browser model-to-SVG drag comparison with region fills on/off. Reports include raw samples, p50/p95, solver errors and degrees of freedom; the pipeline measurement includes packing and callbacks. Both backends include the sparse solver optimizations, so this comparison does not measure their gain over the old dense implementation.

## Region boundary

`find_regions_packed` takes variable-length records `[tag, identity, flag, payloadSlots, ...coordinates]`. The adapter assigns the same call-local identity to equal curve IDs; identities are unsigned 32-bit integers on both native and WASM builds. Tags 0/1/2 are segment (four coordinates), circle (center and radius: three slots), and ellipse (center, major and minor points: six slots). Tag 3 is an arc (center, radius, start and end: seven slots); tag 4 is an elliptical arc (center, major, minor, start and end: ten slots). Tag 5 contains eight coordinates per cubic of a composite spline. The flag is clockwise for arcs, closed for splines, and zero otherwise. The decoder checks tags, integral headers, record lengths, finite coordinates and nonnegative radii before constructing geometry.

The result is `[regionCount, ...regions]`, with each region `[area, ringCount, ...rings]`; the first ring is its outer boundary and the rest are its direct child holes. Each ring contains `[pointCount, ...[x,y], commandSlots, ...commands]`. Numeric commands are `0,x,y` (move), `1,x,y` (line), `2,c1x,c1y,c2x,c2y,x,y` (cubic), `3,rx,ry,rotationDegrees,largeArc,sweep,x,y` (arc), and `4` (close). Coordinates are world-space; arc flags and rotation already encode the SVG convention. JavaScript only changes the sign of Y and formats numbers to five decimal places. Result counts, finite values, command boundaries, flags and closure are validated before exposure to the model.

`kernelRegions.json` captures 120 pre-native arrangements and identifies the unchanged reference source with SHA-256. They cover segments, circles, ellipses, both arc types, composite/closed splines, tangencies, coincident geometry, dangling edges, nested holes, negative-half quantization and imported problem contours. Tests compare face order, vertex order, hole structure, areas and SVG command structure/coordinates; numeric coordinates use 1e-7 absolute plus 1e-10 relative tolerance, with one final 1e-5 SVG formatting unit allowed. Twenty-four dragged benchmark states also compare against the reference, and a binding spy verifies one native region call with no JS intersection/spline callbacks. The full editor suite exercises the routed region API, including export, rendering and hit testing.

Next, reduce costs identified in these measurements and migrate higher-level editing computations where they justify native batching. Document state should move to Rust only after mutation operations have an explicit command/patch contract. Small scalar operations can cost more at the boundary even when larger projections benefit from native loops.

## Trim and extend queries

`GeometryKernel.editing` runs three geometry-only queries in Rust: parameterized curve intersections, trim interval selection, and extension endpoint/target selection. The public `getCurveIntersections`, `getTrimCandidate` and `findExtendCandidate` preserve their signatures and reconstruct original curve references, cutter IDs/types, Vec2 instances and preview data. `trimReference.ts` and `extendReference.ts` retain the pre-routing calculations for the TypeScript fallback. `executeTrim`, `executeExtend`, constraint transfer, document ownership, transactions and undo/redo remain in TypeScript; their mutation code is unchanged.

`curve_editing(curves, settings)` reuses the region curve record format. The first record is the target; the rest are candidate cutters. Settings are `[mode, cursorX, cursorY, controlSpline]`, with mode 0 for intersections, 1 for trim and 2 for extend. The adapter excludes the target identity and preserves the old reserved synthetic extension identities (`__extend_ray__`, `__extend_circle__`, `__extend_ellipse__`). Returned cutter indices are mapped back to the original input array, including duplicate cutters and stable tie precedence.

Mode 0 returns `[count, ...[x,y,param,cutterIndex]]`. Mode 1 returns `[paramA,paramB,startX,startY,endX,endY,startCutter,endCutter,wholeEntity]`. Mode 2 returns `[0]` for no candidate or `[1,endFlag,fromX,fromY,toX,toY,cutterIndex,fullLoop]`. Missing cutters use -1. Record shapes, finite values, flags, parameter domains and source indices are checked before candidates reach the document. Invalid native results propagate without silently executing a second algorithm.

The port retains endpoint exclusion at 1e-4, stable parameter sorting, all-retained-point deduplication, open and cyclic trim intervals, whole-entity removal for closed curves with fewer than two cuts, and the closed control-spline distinction. Extension retains nearest-end ties, the 50,000-unit search ray, 50-unit fallback, degenerate direction fallback, angular guards and full-circle/ellipse conversion. Circular and elliptical extension use the original world-coordinate angles; trim parameters retain their SVG-angle convention. Geometry helpers are shared with native region construction, while extension's world-space ellipse parameterization intentionally retains its unclamped legacy radii.

`kernelEditing.json` captures 256 scenes with four cursor probes each and SHA-256 hashes of both reference modules. Tests compare sorted cuts, interval endpoints, cutter metadata, extension edges/targets and previews. Additional tests cover off-curve cursors, boundary validation, one-call native routing without JS intersection/spline callbacks, and document constraint preservation with undo/redo. Coordinates and parameters use 1e-8 absolute plus 1e-10 relative tolerance; object key order is irrelevant, while geometric array order and cutter precedence are preserved.

The [editing query benchmark](../benchmarks/results/editing.md) measures these queries separately from solver, curve collection, document changes and rendering. Run it with `npm run bench:editing` after building the kernel.

## Fillet geometry

`GeometryKernel.fillet` moves fillet evaluation, extended-curve projection, tangent-circle construction and maximum-radius search into Rust. Supported inputs are segments, circular arcs and fit/control splines represented as cubic segments. Each fillet or maximum-radius query crosses the WASM boundary once; iteration, continuation in radius, reversed curve order and binary search stay native. Preview and commit consume the same result. Connectivity discovery, endpoint IDs, constraint remapping, document mutation and undo/redo remain in TypeScript.

The original numerical implementation is retained in `src/math/filletReference.ts`, with spline calculations imported directly from `splineReference.ts`. The TS fallback calls it without packing. Unsupported curve types keep their previous reference behavior; a failure from a native query propagates. `kernelFillet.json` captures 102 pre-routing fillet/radius queries and 80 evaluation/projection probes. Tests compare both backends to these snapshots, check 120 deterministic transformed curve pairs with actual WASM, and exercise existing fillet constraints, pattern links and history.

API 13 adds `fillet_geometry(curves, settings)` using the existing variable-size region curve records. Settings are `[mode, a, b, hasCorner, cornerX, cornerY, click1X, click1Y, click2X, click2Y]`. Modes are 0 evaluation (`a=t`), 1 projection (`a=x,b=y`), 2 fillet (`a=radius`), and 3 maximum radius (`a=max,b=min`). Evaluation returns `[pointX, pointY, tangentX, tangentY, normalX, normalY]`; projection returns `[t, pointX, pointY, distance]`. Fillets return `[1, centerX, centerY, radius, t1X, t1Y, t2X, t2Y, clockwise, cornerX, cornerY, midX, midY, bisectorX, bisectorY, param1, param2]` or `[0]` when infeasible. Radius search returns `[1, radius]` or `[0]`. Inputs and result layouts are validated; empty-spline projection preserves its infinite-distance sentinel. Public wrappers preserve `Vec2` results, endpoint IDs and borrowed corner/degenerate-point identity.

The port retains the reference's 24 Newton iterations, 1e-3 signed-distance tolerance, radius continuation in steps of at most five, spline-endpoint branch guards, ten binary-search iterations and tenth-unit radius rounding. Arc evaluation still clamps to its span, including the existing unit-X tangent at its final endpoint; spline extensions retain the existing 100-unit parameter scale. This stage preserves those conventions rather than changing fillet behavior. Rebuild generated WASM assets after updating to API 13.

Fillet offset sides at a shared endpoint are anchored to its local curve normals, rather than to the initial radius guess. This prevents a turning spline from selecting the exterior side of an acute arc/spline corner (the Point-94 regression). Disjoint curves retain the seed-based side selection. The recorded 102-query results remain unchanged; the reference source hash includes this correction.

Multiple fillet previews are committed in one deferred solve and one history transaction. When two previews use opposite ends of the same spline, the document extracts the retained interval once from the original cubics and attaches both fillet arcs to its final handles. Overlapping bounds reject the batch before mutation. Numeric queries and preview results still use the selected kernel.

Fillet previews shorten visible arcs and fit/control spline paths at the same endpoint selections used by commit. Spline previews extract a single retained cubic interval for cuts at both ends, and preserve linear endpoint-extension behavior. Original hit paths remain selectable; preview rendering changes neither document geometry nor history, and cancellation restores the original paths.

## Chamfer geometry

`GeometryKernel.chamfer` prepares a corner from its vertex and two far endpoints, then calculates equal-distance, two-distance and distance/angle chamfers in Rust. Each preparation or calculation is one WASM call. Connectivity discovery, primitive IDs, constraints, document mutations, preview formatting and history remain in TypeScript. The direct TS fallback is retained in `src/math/chamferReference.ts`; both paths return the existing `Vec2`-based public results and error messages. The two-distance commit path assigns dimension expressions to the flipped sides, so parameter recomputation and undo/redo preserve the geometry shown in the preview.

API 14 adds `chamfer_geometry(geometry, settings)`. Settings are `[operation, mode, distance1, distance2, angleDegrees, flip]`, with mode 0 equal distance, 1 two distances and 2 distance/angle. Operation 0 accepts `[vertexX, vertexY, other1X, other1Y, other2X, other2Y]` and returns `[1, dir1X, dir1Y, dir2X, dir2Y, len1, len2, cornerAngleRadians]` or `[0]` for a rejected corner. ## Batched editor queries (API 22)

`GeometryKernel.queries` adds curve bounds, screen-space hit distances, nearest hit/snap selection, crossing/contained box selection and point-in-region tests. The editor batches each hit-priority group, the eligible snap candidates and box-selection curves; region hover submits all cached regions together. Standalone curve bounds and distance helpers use the same boundary. Point/vector arithmetic, document bounds aggregation, viewport transforms, hidden-handle filtering, dragged-point exclusions, entity priority and selection/history ownership stay in TypeScript. Custom primitive method overrides retain polymorphic dispatch. `aabbReference.ts` and `hitTestReference.ts` freeze the previous arithmetic; the TypeScript backend uses `queryReference.ts`.

`geometry_queries(curves, settings)` accepts two packed `Float64Array`s. Settings are `[mode, x, y, a, b]`. Modes 0–5 reuse the region curve records (including entire composite splines): 0 bounds; 1 distances with threshold `a`; 2 closest hit with threshold `a`; 3 closest snap with threshold `a` and angular tolerance `b`; 4 crossing box and 5 contained box, with min `(x,y)` and max `(a,b)`. Mode 6 tests point `(x,y)` against regions packed as `[regionCount, ringCount, vertexCount, x, y, ...]`, one outer ring followed by holes for each region. All counts and numeric payloads are validated. Invalid/unbounded curves yield no display bounds before entering the packed bounds query; native query failures otherwise propagate.

Bounds return five slots per curve `[present,minX,minY,maxX,maxY]`, distances two `[present,distance]`, closest five `[index,distance,x,y,param]` with index -1 for no match, and box/region tests one boolean slot per input. Absent payload slots are zero. Snap `param` is the segment interpolation parameter, preserving world-space line interpolation; it is zero for other types. Hit queries ignore the snap position slots. The adapter validates lengths, flags, finite values, ordered bounds and nearest-result indices/distances.

Hit and snap curves are transformed to screen coordinates in JavaScript before packing, preserving pixel-based floors and tolerances. Closest selection processes curves in their original order and shrinks the hit threshold after every improvement; snapping keeps its original angular tolerance separately. Equal distances retain the first candidate. Hit/snap queries preserve existing radial ellipse projection, arc endpoint wrapping and screen-space sweep conventions. Full ellipse box checks retain 36-step sampling, circles retain their perimeter rules, and splines retain endpoint/edge crossing tests. Circular and elliptical arc crossing checks use the corrected world-space sweep and analytic box-edge intersections described below. It introduces no new geometric accuracy guarantee. Tests compare the frozen reference across every curve type, holes and boundaries, degeneracies, zoom/pan and skew axes, plus actual WASM editor batching and unchanged document snapshots/history.


Arc crossing selection uses clockwise as decreasing parameter in world coordinates, matching rendered geometry and contained selection. The original TypeScript box query used the opposite sweep and also accepted a box containing only the arc center; API 22 initially preserved those bugs during the port. Both active backends now test endpoints and analytic intersections of the swept conic with the four box edges. This also detects narrow boxes and tangencies without selecting chord approximations, and accepts nondegenerate elliptical arcs below the old 0.01 sampling floor. Root/span and edge comparisons allow only floating-point rounding tolerances. The packed layout is unchanged; the frozen pre-migration reference files remain unchanged. Regressions cover both sweeps, reversed endpoints, angle seams, center-only boxes, tangencies, tiny rotated elliptical arcs, and actual right-to-left editor selection across zoom/pan values.

## Offset spline refinement (API 24)

The output is `[threshold,vertexCount,...x,y,pathCount,...paths,circleCount,...cx,cy,r,closedSplineCount,...splines]`. A spline payload begins `[pointCount,handleCount]`, followed by point pairs and `[h1x,h1y,h2x,h2y]` handles. Path-spline points exclude the two shared vertex endpoints; handles include them. Closed spline points/handles omit the repeated seam; two-anchor closed cubic paths are valid (including narrow retraced strokes) and must not be rejected by the adapter. Control-hull rejection retains its 1e-4 allowance, final branch residuals must be below 1e-5, and the analytic loop guards retain their previous thresholds. Distinct parameter pairs at the same world-space location are retained. This stage adds no new intersection-accuracy guarantee or spatial acceleration structure.

The old TypeScript self-intersection algorithm has been removed. The public query requires the native capability and reports an explicit error when it is unavailable; non-finite inputs are rejected without a fallback. Other TypeScript reference operations remain available, but spline editing and region preprocessing that need self-intersections require Rust/WASM. `kernelSplineSelf.json` preserves 59 queries captured before routing under both original backends and the historical hash of the deleted source. Native results are checked against these fixed expectations without executing the old algorithm. TS control-flow comparison tests and benchmarks inject only this native capability into their reference backend; benchmark reports identify it as `selfIntersectionsBackend: wasm`. Tests cover transformed loops, open/closed seams, adjacency, tangency, coincident/retraced/collapsed geometry, distinct parameter pairs at one crossing, mathematical branch residuals, input preservation, malformed buffers and one-call dispatch. Existing Trim/Break/Extend, region and history regressions exercise the shared native search. Rebuild generated WASM assets after updating to API 26.

## Precise spline cut coordinates (API 27)

Spline Trim/Break intersection parameters now use `spline::intersection_param` after the crossing has been located. Previously, `editing::curve_intersections` converted each accurate 2D hit back to a parameter using the general 12-sample/10-step projection. Evaluating the spline at that approximate parameter moved the eventual cut point; the `sketch_1794821487930.svg` regression exhibited approximately 0.005–0.035 world-unit discrepancies even though the original crossing coordinates were accurate.

The cut-specific path seeds from the existing projection, retains the selected cubic branch, compares both cubic endpoints and applies up to 20 damped derivative corrections to minimize the distance to the known intersection. Corrections remain in [0,1] and must decrease the squared distance. The corrected parameter is used by both preview and commit, so interval extraction retains the original cubics and shared endpoints are recognized correctly. The source candidate/intersection search, deduplication and general projection used by the solver, cursor, text and other queries remain unchanged. Parameters at true open endpoints now pass the existing endpoint exclusion correctly rather than becoming artificial near-end cuts. Historical TypeScript fallback arithmetic remains frozen.

API 27 keeps the existing packed layouts and rejects older generated assets through the version check. The scene regression tests Break on Spline-3 at cursor (54,19), hit/parameter round-trip errors below 1e-8 world units, exact retained cubic controls within that tolerance, shared cut-point connectivity, source-point preservation and undo/redo. On the supplied scene, observed post-refinement discrepancies are below 2e-11 world units; this is a measured regression result, not a universal certified error bound. Native unit tests additionally check known curve points across scales and exact multi-cubic endpoints. Native editing expectations for spline targets use an independent 64-step scalar minimization oracle; the original pre-routing fixtures and their source hashes remain unchanged. Rebuild with `npm run build:kernel` after updating.


## Whole-spline cuts (API 28)

`splitSplineAtParam`, `trimBezier` and `extractSplineInterval` now run complete cut operations in Rust when the native spline kernel is active. Each operation packs its source cubics once and makes one `spline_geometry` call, including wrapped intervals and no-op cuts. Rust selects source spans, calculates local parameters, applies de Casteljau subdivision and orders the retained pieces. The shared `sketcher_core::spline_editing` implementation also replaces the duplicate interval arithmetic in native region construction. Document mutations, constraints, undo/redo and SVG formatting remain in TypeScript.

Modes 11/12/13 use settings `[mode,start,end,0]`, with eight coordinates per source cubic and empty handles/knots. Mode 11 splits an entire nonempty spline (`end` must be zero), mode 12 trims exactly one cubic, and mode 13 extracts a forward or seam-wrapped interval. Every output piece is `[sourceIndex,originalPoints,x0,y0,x1,y1,x2,y2,x3,y3]`. The provenance mask is 0, 1 (original start), 8 (original end) or 15 (all original controls). Mode 11 prefixes the flattened pieces with the left-piece count; mode 13 prefixes them with a 0/1 flag indicating the original whole source array. Mode 12 returns one piece without a header. The adapter validates finite coordinates, counts, indices, masks, retained source coordinates, split ordering and the shared split point before reconstruction.

The public adapter preserves the original `Vec2` object sharing: untouched cubics keep their source arrays, unchanged endpoints keep their source points, split halves share one new cut point, and whole-interval no-ops return the source array. No-op provenance comes from Rust rather than repeating span calculations in JavaScript. Existing 1e-5 interval/whole-span tolerances, 1e-6 span/subdivision thresholds, clamped whole-spline split parameters, degenerate endpoint halves and tail-then-head seam order are unchanged. Empty intervals remain valid; splitting an empty spline reports an error. Single-cubic trim retains finite extrapolation behavior. Non-finite cut inputs/results and reversed intervals with endpoints outside the supported wrap range are rejected. These changes do not tighten the existing cut thresholds.

The optional native methods leave the frozen `splineReference.ts` path available to the TS reference backend and custom kernels that omit these capabilities. Its source hash and all 160 existing `kernelSplineEditing.json` cases remain unchanged. Additional tests compare numerical results and object-sharing graphs across scales, collapsed geometry, span boundaries, seam wraps, no-op and near-zero intervals; they also check single-call routing, malformed buffers/provenance and native failure propagation. Native unit tests independently verify parameterized cubic shape and decoder contracts. The full WASM suite exercises the existing Trim/Break precision, Fillet/Chamfer shape and preview, region and history regressions. Rebuild generated assets with `npm run build:kernel` after updating to API 28.


## Offset coincidence and connectivity (API 29)

`GeometryKernel.topology` calculates coincidence reachability and ordered primitive incidence in Rust. Offset's chain selection, extension, deselection and continuation queries prepare one call-local graph snapshot per action, then reuse it for every traversed vertex. Spline direction checks while collecting an offset query share one lazily prepared snapshot too. ID lookup, primitive eligibility (construction geometry, spline handles and closed curves), selection decisions, chain mutation and document history stay in TypeScript. The graph is not cached between actions, so coordinate edits, changed constraints and undo/redo cannot reuse stale connectivity.

The graph preserves the 1e-3 world-unit point tolerance, Euclidean distance check, transitive coincidence links, implicit origin, missing constraint endpoints and built-in axis points. A spatial hash narrows finite point comparisons; candidates are sorted back into document order before insertion. Coordinates outside the exact integer-cell range use a conservative scan. Direct point-group queries retain the original stack traversal and insertion order: constraint neighbors first, listed geometric neighbors next, then the implicit origin. Primitive neighbors retain line/arc/elliptical-arc/spline collection order and exclude primitives whose two endpoints are both reachable.

Built-in points returned by `PointMap.get` need not occur in `PointMap.values`, so geometric reachability can be directed. The prepared graph uses iterative strongly connected component discovery and per-component reachable sets rather than assuming undirected equivalence. Endpoint incidence lists avoid scanning every primitive for every component. Snapshots contain point-to-component labels, reachable members and oriented primitive connections. Adapter validation checks counts, unique members, label membership, ordered primitive indices and each connection's original endpoints before restoring document IDs. Native failures propagate; the TS reference backend and non-finite legacy document coordinates retain the independent frozen implementation in `offsetTopologyReference.ts`.

API 29 adds `topology_queries(points,links,endpoints,settings)`. Points use `[hasPosition,listed,x,y]`, while links and primitive endpoints contain pairs of call-local point indices. Settings are `[mode,tolerance,originIndex,seedIndex]`; absent origin is -1. Mode 0 returns `[count,...orderedMembers]` for one seed. Mode 1 requires seed -1 and returns `[componentCount,...pointLabels, ...components]`, where each component is `[memberCount,...members,connectionCount,...[primitiveIndex,connectedPointIndex,otherPointIndex]]`. Buffers, arities, flags, positive tolerance, finite values and indices are validated at the native boundary. Older generated assets are rejected; run `npm run build:kernel` after updating.

`kernelTopology.json` records 226 point queries and 304 chain actions over 16 pre-routing scenes, with a hash of the independent reference. It covers open/closed chains, reversed orientation, branches, geometric seams, tolerance boundaries, missing endpoints, constraints, built-ins, service handles, construction geometry and extreme coordinates. Tests additionally cover one native call per action, shared spline-direction queries, fresh geometry after undo/redo, malformed buffers, native error propagation and invalid-coordinate compatibility. Native unit tests exercise directed built-in reachability and a 10,000-node constraint chain without recursion.

Run `node --import tsx --import ./test/helpers/wasmKernel.ts benchmarks/topology.ts` for a warm-kernel comparison that includes snapshot packing, WASM validation and JS chain assembly. On the development machine, median-of-five timings for selecting an open chain were approximately 1.03 → 0.56 ms for 200 lines and 28.9 → 3.35 ms for 1000 lines (about 1.9× and 8.6× faster). Source chains are checked for identical results before measurement. These are workload-specific query measurements and exclude rendering and solver commit.


## Text geometry (API 30)

`GeometryKernel.textGeometry` lays out complete font-extracted outlines in one Rust query. `generateTextSvgPathData` retains its public signature and returns the existing two-decimal SVG path. TypeScript uses the font library for shaping, advance widths, raw metrics and glyph paths at the requested text height. Repeated glyphs share outline extraction within a single request; there is no persistent font-outline cache across requests. Rust calculates spacing, alignment, multiline baselines, both reflections, curve-distance placement and every outline/control-point transform. Reading fonts, extracting glyph commands, constructing the editor document and formatting SVG remain in TypeScript. Rectangle rendering that uses browser SVG text is unchanged; outlined export and text-on-path geometry use the native query.

Path text prepares its distance table and samples all glyph frames inside that same Rust call, sharing `curve_path::prepare/sample`; there are no per-glyph JS callbacks or separate curve-path queries. Rectangle layout preserves the original one-unit margins, 1.25 line spacing, empty-line baseline positions, ascender/descender fallbacks, skewed rectangle axes and block-centered vertical reflection. Path layout preserves negative spacing, fit-to-path gap redistribution (including the single-glyph case), signed distance continuation/clamping for each curve family, cap-height placement when vertically flipped and final CAD/SVG Y inversion. The existing 1e-3 short-path/rectangle thresholds and path sampling tolerances are unchanged. Glyph commands M/L/Q/C/Z and contour order are retained.

API 30 adds `text_geometry(glyphs,outlines,geometry,settings)`. Glyph records are `[lineIndex,advanceWidth,commandCount]`; advance widths are font units, while outline coordinates already use the requested text height. Outline records are tags M=0, L=1, Q=2, C=3, Z=4 followed by 2/2/4/6/0 coordinates. Geometry is either eight rectangle-corner coordinates or one existing packed region-curve record. Settings are `[mode,height,unitsPerEm,ascender,descender,capHeight,characterSpacing,alignment,verticalAlignment,flags,lineCount]`: mode 0 is rectangle and 1 is curve; alignment codes are left/center/right and top/middle/bottom respectively. Flags are horizontal flip=1, vertical flip=2, fit-to-path=4, below=8, SVG coordinates=16. The result uses the same command stream format without a header. The decoder validates flags, finite buffers/results, positive units per em, bounded counts, ordered glyph lines, complete command arities and target geometry. The JS adapter also verifies command sequence, coordinate counts and absence of trailing output. Native errors propagate.

The optional capability retains the independent frozen `textPathReference.ts` implementation for the TypeScript backend and custom kernels without native text support. `kernelTextGeometry.json` captures 189 queries before routing under both original backends, including unrounded commands and SVG strings. Source/font hashes identify the unchanged reference math and bundled fonts. Cases cover synthetic quadratic/cubic outlines with holes and zero-width glyphs, Arial/Times/Courier, multiline/CRLF text and blank lines, all alignment/reflection switches, both coordinate systems, every supported curve family, large/negative spacing, fit-to-path and degenerate targets. Tests compare unrounded geometry, font extraction, public SVG structure and input preservation; they also exercise one-call dispatch, malformed native buffers/results and the existing text tool/export regressions. Rebuild generated assets with `npm run build:kernel` after updating to API 30.

A repeatable warm-kernel comparison is available with `node --import tsx --import ./test/helpers/wasmKernel.ts benchmarks/textGeometry.ts`. It measures the full font-extraction, geometry and SVG-formatting path; rendering and font loading are excluded.


## Below-path capital-line contact (API 31)

Unflipped `below` path text now uses the actual capital height (`H` glyph bounds scaled from font units), rather than the full em height, as its normal offset. The capital line touches the path's glyph frame without the previous em-to-cap gap; glyph size, advances and spacing are unchanged. Vertically flipped `below` text keeps its baseline on the path, and both existing `above` placements retain their offsets. CAD/SVG inversion and horizontal reflection apply after the same placement calculation.

## Overlong text alignment on open paths (API 32)

Open spline and segment text without fit-to-path now retains the signed alignment offset when its measured run is longer than the source path. Right alignment anchors the run's end at the path end; center alignment distributes the overflow across both ends. Glyph frames outside the open path continue along its endpoint tangent, preserving glyph spacing instead of stacking glyphs at the clamped endpoint. Short text and fit-to-path retain their existing placement. General curve sampling still clamps open-path distance queries; this continuation is specific to overlong text geometry. Closed-path and conic continuation rules are unchanged.

The TS fallback extends only its temporary reference path with exact tangent-line cubics, preserving the frozen pre-migration algorithm and original source geometry. Existing captured fixtures remain historical; intentionally changed open-path cases compare against the corrected independent reference. Regressions check negative alignment offsets, distinct glyph frames and endpoint continuations on straight, reversed and curved open splines, including horizontal reflection and CAD/SVG coordinates. API 32 retains the buffer layout and rejects cached binaries that still clamp alignment to zero. Rebuild generated assets with `npm run build:kernel`.

Text SVG serialization rounds a copy of the transformed commands before opentype packs coordinates. Its original formatter can merge a negative value rounded to zero with the previous coordinate, or produce `NaN` when a fractional part near an integer is written in scientific notation. Either error makes browsers stop drawing the remaining text. Both backends use the corrected formatter; native outline coordinates retain their full precision. The reference layout only adds an optional serializer callback, and fixture source hashes reflect that hook without recapturing historical geometry. SVG comparisons serialize those original captured outlines with the corrected formatter.

Regressions parse the entire emitted M/L/Q/C/Z stream, cover near-zero and near-integer coordinates in every command slot, and exercise the imported bilingual wave-spline scene through the editor renderer with both backends. A browser check verifies that the full right-aligned text reaches the final spline endpoint.


## Primitive construction (API 33)

`GeometryKernel.construction` moves the numerical construction routines from the editor tools into `sketcher_core::construction`. Circle, arc, slot and polygon previews and creation share the same math adapters. This includes circumcircles, the collinear preview fallback, circles through a chord with a fixed diameter, two-line tangent circles with free or locked radius, three-line tangent circles, three-point/center/tangent arcs with locked dimensions, linear and arc-slot centers/outlines/radii, and polygon edge/vertex geometry. `getCircumcircle` retains its public vector API. Polygon vertices are returned as one batch, including for document creation; line/arc direction tests accept screen points, while arc construction receives the viewport orientation. Viewport conversion, cursor history, popup state, snap decisions, constraint creation, IDs and transactions stay in TypeScript.

Construction retains the existing degeneracy thresholds, radius limits, nearest-cursor choices, strict candidate tie order, three-line pivoting order, small/large arc selection, slot radius clamps, polygon orientation and ordinary `Vec2` results. Linear slots retain sharing of unchanged source centers. A zero/degenerate or overflowing construction returns no result; malformed records and non-finite input are boundary errors. The optional capability keeps the independent `constructionReference.ts` fallback for the TS backend and custom kernels. Existing circle/arc drawing-state rules and simple UI distance/angle tracking are unchanged; this is not a claim that every tool arithmetic expression has moved to Rust.

API 33 adds `construct_geometry(mode,data)`. `CONSTRUCTION_MODES` defines the stable tags 0–18 and `CONSTRUCTION_ARITIES` their fixed input sizes. Modes are circumcircle, preview circle, chord circle, offset-line intersection, two-tangent circle, fixed-radius two-tangent circle, three-tangent circle, three-point arc, tangent arc, center arc, slot centers, slot outline, slot radius, arc-slot geometry, arc-slot radius, polygon edge, polygon vertices, point at distance and arc-through-point direction. Data contains coordinate pairs followed by numeric parameters and explicit flags. Points use `[x,y]`, tangent lines use `[px,py,nx,ny]`; arc lock settings are `[hasRadius,radius,hasAngle,angleRadians,viewOrientation]` and view orientation is -1 or +1. Center-arc angle -1 denotes an unlocked angle. Slot mode codes are center-to-center=0, center-point=1, overall=2. Polygon vertex count is normalized in the public adapter and bounded at 100000 at the native boundary.

The result is `[0]` for a missing construction or `[1,...values]` for success. Fixed-size outputs are validated in the JS adapter, including boolean direction fields; polygon output contains exactly two coordinates per vertex. Native errors propagate. The core validates arities, finite values, tags, flags, mode enums and bounded polygon counts. Rebuild generated assets with `npm run build:kernel`; older binaries are rejected by the API version check.

`kernelConstruction.json` captures 540 queries before tool routing, together with hashes identifying the original tool sources and the independent reference. Comparisons exercise both native and fallback results, both viewport orientations, locked radius/angle combinations, slot variants, polygon winding, invalid/collinear constructions and multiple scales. Tests also cover native batching without curve/spline callbacks, malformed outputs/inputs, input immutability and the existing editor tool suite. Independent Rust tests check circle-line contact, chord sides, arc tangents, concentric slot boundaries and polygon edge/vertex consistency.
