# Rust geometry kernel

The editor routes intersections between segments, circles, ellipses and cubic Bezier segments through a versioned `GeometryKernel` boundary. Circular and elliptical arcs use the same kernel calculations, with the existing arc-span filtering and point deduplication in the TypeScript adapter. Composite splines are expanded into cubic pairs in their original traversal order; their intersection calculations run in the active kernel.

In WASM mode, the numerical constraint-solving loop also runs in Rust: sparse Jacobian rows and normal equations, sparse LU decomposition with partial pivoting, Levenberg–Marquardt damping, projected lower bounds and sparse nullspace analysis. Rust also evaluates residuals and Jacobians for 32 built-in constraint classes: fixed, drag point, coincident, concentric, horizontal, vertical, radius, equal radius, distance, equal length, midpoint, point on circle, point on line, parallel, perpendicular, collinear, angle, tangent line/circle, tangent circle/circle, ellipse axis, point on ellipse, circular arc endpoints, elliptical arc endpoints, point-to-line distance, symmetry, circular pattern, rectangular pattern, offset, origin distance, line-to-axis distance, point on spline and solve-time automatic spline handles. Customized constraints and unusual nonclamped B-spline knot vectors retain batched TypeScript evaluation. The spline constraints construct and project curves entirely in Rust. Standalone construction, evaluation, projection and cubic splitting used by rendering, snapping and editing now use the selected kernel too. Parameter ownership, document operations, SVG formatting and viewport transforms remain in TypeScript. The original spline arithmetic is retained in `src/math/splineReference.ts` as an independent reference.

`getCurveIntersections` batches primitive pairs to reduce JS/WASM calls. A query containing composite splines submits all cubic combinations in the same batch, then filters spans and deduplicates the combined results. In WASM mode, region construction runs entirely in Rust through one `find_regions_packed` call: conservative bounds, exact intersections, cuts and spline projection, curve sampling, graph construction, iterative bridge removal, face traversal, nested holes and numeric boundary commands. Cubics use control hull bounds and arcs use full conics, padded for the existing contact tolerances. Segment/ellipse pairs retain exact evaluation because their discriminant tolerance is not a fixed world-space distance. The inexpensive bounds scan remains O(n²). Kernel data contains world-space coordinates and call-local identity tags, without DOM, viewport or document dependencies.

`src/math/regionsReference.ts` retains the pre-native TypeScript algorithm, including the bounds filter. The public region API selects `GeometryKernel.findRegions` when available and otherwise uses this reference. Vec2 reconstruction, SVG string formatting and the point-in-region UI query remain in TypeScript. Native failures propagate rather than silently running a second algorithm. The Rust graph uses numeric nodes and edges; insertion-order vectors preserve traversal order, while hash maps serve only lookup. Quantized keys retain JavaScript rounding at negative halves and the original neighboring-key merge behavior. The 10,000-edge face guard, sampling counts, thresholds, source-edge replacement and direct-child hole rules are preserved.

## Build and run

Install Rust 1.88 or later using your usual toolchain setup, then install the target and the CLI matching the pinned Rust dependency:

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.105 --locked
npm run build:kernel
npm run dev
```

For a production WASM build:

```sh
npm run build:wasm
npm run preview
```

`npm run dev` and `npm run build` load WASM by default. Build the kernel first, or use `build:wasm` to rebuild everything together. `VITE_GEOMETRY_KERNEL=typescript npm run dev` explicitly selects the reference backend. WASM initialization completes before the editor starts. A loading, initialization or API-version failure leaves the TypeScript backend active and logs the cause to the browser console.

`WASM_BINDGEN=/path/to/wasm-bindgen` can select a CLI outside `PATH`. Generated bindings and the binary go into ignored `public/kernel/`; Vite copies them into the production build. Commit `Cargo.lock`, not the generated files. A deployment that builds only the browser bundle must also generate the kernel assets to use the default WASM backend.

## Boundary and next steps

- `crates/sketcher-core` contains native-testable geometry without JavaScript dependencies.
- `crates/sketcher-wasm` validates and decodes numeric buffers and exports API version 19 through `wasm-bindgen`. Older binaries are rejected before use; rebuild the kernel after updating the source.
- `src/kernel` contains the shared contract, TypeScript backend, WASM adapter and browser initialization.
- Each input curve occupies nine `f64` slots: segment `[0, x1, y1, x2, y2, 0, 0, 0, 0]`, circle `[1, cx, cy, radius, 0, 0, 0, 0, 0]`, ellipse `[2, cx, cy, majorX, majorY, minorX, minorY, 0, 0]`, cubic `[3, x0, y0, x1, y1, x2, y2, x3, y3]`. Every input pair produces `[count, x, y, ...]`, including a count of zero for an empty result. Inputs must contain finite coordinates and nonnegative radii.
- Candidate ordering and existing tolerances are preserved. Arc filtering precedes deduplication so a discarded candidate cannot hide a valid arc contact.

The sampled ellipse/conic root finder retains its existing 128 intervals, 28 bisection steps, tolerances and candidate ordering. This migration does not redesign tangency detection or coincident-ellipse handling. Candidates are filtered by arc span before deduplication, so the packed result allows up to 128 raw candidates for ellipse pairs, including degenerate coincidence cases.

Cubic/conic and cubic/segment calculations retain 16 sampling intervals, 28 bisection steps and the additional near-root check at the final sample. Cubic/cubic calculations retain bounding-box subdivision, depth 15, four Newton refinement steps, the cap of 16 candidate contacts and per-pair deduplication at 1e-3. Composite spline results are subsequently deduplicated at 1e-4 after arc-span filtering. The packed protocol allows up to 17 candidates for a pair containing a cubic.

## Numerical solver boundary

`NumericalSolver.solve` dispatches to the selected kernel's optional `solveSystem`; if absent, it runs the TypeScript solver. Both implementations use sparse rows, duplicate-entry merging, sparse normal equations/LU/nullspace analysis and cached linearization across rejected LM steps. The release profile uses `opt-level = 3`. Fully native systems assemble sparse Jacobians directly through `Program.evaluate_sparse`; mixed JS/native systems retain the dense numeric callback buffer before sparse assembly. `src/solver/kernelAdapter.ts` prepares free parameter indices, hard constraints, stiffness and lower bounds, and converts the result to existing parameter IDs and statuses. `src/solver/nativeConstraints.ts` compiles supported constraints once per solve. Custom subclasses or overridden formula methods retain TypeScript evaluation. The staged radius policy, spline-handle preparation and drag constraints in `SketchDocument.solve` retain their existing behavior.

`solve_system` receives the current free values, stiffness, lower bounds, settings `[equations, hardEquations, skipDoF, maxIterations, tolerance, initialLambda, lambdaFactor, minLambda, maxLambda]`, and packed native constraints. Each native record is `[kind, allRow, hardRowOrMinusOne, weight, a, b, refCount, ...[freeIndexOrMinusOne, constantValue]]`. A negative parameter index denotes a fixed or missing parameter. Rust validates tags, arities, variants, finite constants, parameter indices and non-overlapping equation rows before solving.

The curved constraints add the following tags. Each point below occupies two references (x, y); angle orientation factors are constant references with index -1.

| Kind | References | a | b |
| --- | --- | --- | --- |
| 14: angle | line endpoints (four points), s1, s2, sign | target degrees | axis scaling: 0 neither, 1 first, 2 second |
| 15: line/circle tangency | center, line endpoints, radius | initial side | unused |
| 16: circle/circle tangency | centers, radii | target: 0 sum, 1 first minus second, 2 second minus first | unused |
| 17: point on ellipse | center, major-axis point, minor-axis point, point | unused | unused |
| 18: elliptical arc endpoints | center, major-axis point, minor-axis point, start, end | unused | unused |
| 19: circular arc endpoints | center, start, end, radius | unused | unused |
| 20: point-to-line distance | point, line endpoints | target distance | side |

Shared-point circle tangency reuses kind 10 (point on line through the centers). Ellipse axis perpendicularity reuses kind 12 with an aliased center reference. These preserve the original numerical Jacobians, including perturbing every reference to a shared parameter together. Circular arc endpoints retain their analytic Jacobians.

`src/solver/nativePatterns.ts` expands composite constraints into multiple records in their original equation order. Suppressed copies produce no records; pattern radius pairs reuse kind 5 with pattern radius first. Each record carries both its full-system row and its hard-system row, so empty, soft and mixed JS/native constraints preserve their offsets. If any record cannot be compiled, the entire constraint retains JS evaluation. Native record buffers are appended without spreading them into JavaScript function arguments, including a single variable-size spline record. A 10,000-point packing test checks this limit without attempting a dense solve of that size.

| Kind | References | a | b |
| --- | --- | --- | --- |
| 21: symmetry | point 1, point 2, line endpoints | 0 line, 1 origin | unused |
| 22: circular pattern point | center, source, copy, constant copy index, constant quantity | total degrees | 0 full, 1 partial, 2 symmetric |
| 23: rectangular pattern point | source, copy, line 1 endpoints, line 2 endpoints, constant i, j, direction 1, direction 2, line 1 present, line 2 present | distance 1 | distance 2 |
| 24: offset line endpoint | child endpoint, original line endpoints | distance | side |
| 25: offset circle | child center, original center, child radius, original radius | distance | side |
| 26: offset spline point | child point, constant base point, constant normal, constant side | distance | unused |

Rectangular direction flags are 0 for one direction and 1 for symmetric; presence flags are 0/1. Rust retains the circular quantity rounding, signed copy distributions, rectangular fallback directions at length <= 1e-6, analytic pattern derivatives and the original unfiltered point coefficients. Offset line residuals retain the left-hand sign, 1e-9 length floor and 1e-6 forward differences. All offset Jacobians intentionally drive only child parameters, including the original alias behavior, so master geometry remains unchanged unless another constraint moves it. Spline offsets use stored base positions and normals; this does not migrate spline construction or projection.

Origin and axis constraints use two additional records:

| Kind | References | a | b |
| --- | --- | --- | --- |
| 27: origin distance | point x, point y, constant side | target distance (unused for coincidence) | 0 radial, 1 horizontal, 2 vertical, 3 coincidence |
| 28: line-to-axis distance | selected coordinate of endpoint 1, selected coordinate of endpoint 2, constant side | target distance (unused for collinearity) | 0 distance, 1 collinear |

Kind 27 produces two equations for coincidence and one otherwise; kind 28 always produces two, even for shared endpoints. The compiler selects y coordinates for distance to the X-axis and x coordinates for distance to the Y-axis. These refer to the world origin and axes, independently of similarly named map parameters. The analytic Jacobians retain the 1e-7 radial length floor, division-then-weight operation order and 1e-12 coefficient cutoff. Zero-distance horizontal/vertical equations and coincidence ignore the side; collinear equations ignore both side and distance. Unspecified point orientation retains radial behavior.

Spline records are variable-size and validated before indexing:

| Kind | References | a | b | Equations |
| --- | --- | --- | --- | --- |
| 29: point on spline | target x/y, N curve points; fit tail: N blocks `[constant enabled, h1x, h1y, h2x, h2y]`; control tail: zero or N+4 constant knots | 0 fit, 1 control | N | 1 |
| 30: automatic handles | N fit points, H blocks `[constant fit index, child1x, child1y, child2x, child2y]` | N | H | 4H |

`src/solver/nativeSplines.ts` compiles these records; `crates/sketcher-core/src/constraints/splines.rs` evaluates them. Cubic B-splines preserve linear/quadratic degree elevation and Boehm knot insertion. Fit curves preserve the natural handle formula, 1e-4 closed-seam test, 1e-6 direction threshold, curvature clamp and explicit-handle overrides. Valid clamped nondecreasing explicit knot vectors run natively; other full-length vectors retain JS evaluation. Short knot vectors retain uniform-knot behavior, and knots on curves with fewer than five points remain unused.

Projection retains 12 sample steps per segment, 10 refinement iterations with constants 0.382/0.618, strict comparisons, normalized segment indexing and the 1e-7 tangent-length floor. Its scaled two-coordinate norm matches the captured TS behavior on retraced curves, where one rounding bit can select a different equally close branch. The point-on-spline residual remains signed distance along the projected normal, including the reference behavior beyond endpoints. Its Jacobian uses the existing 1e-5 forward differences and relevance metadata.

Automatic handles retain direct child coefficients plus numerical fit-point derivatives in fit-point insertion order, including the original double contribution when a fit parameter aliases a child. This class ignores its weight in both implementations and remains a solve-time constraint, without changing document serialization. Customized private natural-handle helpers retain JS evaluation.

The `spline_geometry(points, handles, knots, settings)` WASM export serves the editor and independent verification. Settings are `[mode, targetX, targetY, parameter]`; mode 0 returns natural handle coordinates (four slots per point), mode 1 fit cubics, mode 2 control cubics (eight slots per cubic). Mode 3 retains the combined verification query `[parameter, distance, projectedX, projectedY, tangentX, tangentY, sampleX, sampleY]`. Modes 4/5 evaluate normalized position/tangent and return two coordinates. Modes 6/7 evaluate a single cubic/derivative at an unclamped parameter; mode 8 splits one cubic into two (16 coordinates). Mode 9 projects and returns only `[parameter, distance, projectedX, projectedY]`. Scalar evaluation and tangent calls do not run the projection search.

`GeometryKernel.spline` exposes these operations as typed points, cubics, handle pairs and projections. `src/kernel/splineWasm.ts` validates output counts, finite coordinates and projection bounds before returning geometry. Unusual knot vectors and non-finite legacy arguments retain reference behavior. The public `src/math/spline.ts` API still returns `Vec2` instances and preserves shared split endpoints, B-spline joins, empty-curve projection identity and unmodified input data. Its higher-level split/trim/interval functions compose native cubic splits; SVG string generation and viewport transforms remain in TS. The default TS path calls the reference functions directly without repacking vectors. JS constraint formulas import the reference module directly so that they remain independent of the active geometry backend.

`kernelSplineEditing.json` adds 160 pre-routing split, trim and interval snapshots, including clamped and extrapolated parameters. The routing tests verify reference-file identity, vector semantics, every native operation mode and corrupt-result rejection. The existing spline, snapping, region, history and serialization tests now exercise the public routed API with WASM as well as the optimized sparse solver.

Systems entirely covered by native formulas need only accepted-state commit callbacks. For mixed systems, Rust requests one callback per phase that has uncovered rows; TypeScript fills only those rows in the full-sized buffer, then Rust fills native rows:

| Mode | Response |
| --- | --- |
| 0 | All residuals |
| 1 | All residuals followed by a dense row-major Jacobian |
| 2 | Hard-constraint residuals |
| 3 | Hard-constraint Jacobian |
| 4 | Commit the accepted parameter state; return an empty array |

Evaluation inputs and outputs are copied numeric buffers. Rust retains the authoritative trial state during a solve, so callback re-entry or WASM memory growth cannot invalidate a JavaScript view. The result is `[status, iterations, initialError, finalError, DoF, fixedCount, ...values, ...fixedIndices]`, with status tags 0 (converged), 1 (under-constrained), 2 (over-constrained). API compatibility and result shapes are checked before the result is exposed to the model. Exceptions propagate instead of silently running a second solver after partial commits.

Native Jacobians retain the original analytic derivatives, forward/central finite differences, step sizes, derivative cutoffs and accumulation of shared parameter references. The `evaluate_constraints` export evaluates native rows independently for parity tests; its settings are `[equations, hardEquations, mode]` using the same modes above.

The [performance suite](../benchmarks/README.md) now provides six deterministic large scenes, Node solver/region measurements and a browser model-to-SVG drag comparison with region fills on/off. Reports include raw samples, p50/p95, solver errors and degrees of freedom; the pipeline measurement includes packing and callbacks. Both backends include the sparse solver optimizations, so this comparison does not measure their gain over the old dense implementation.

## Region boundary

`find_regions_packed` takes variable-length records `[tag, identity, flag, payloadSlots, ...coordinates]`. The adapter assigns the same call-local identity to equal curve IDs; identities are unsigned 32-bit integers on both native and WASM builds. Tags 0/1/2 are segment (four coordinates), circle (center and radius: three slots), and ellipse (center, major and minor points: six slots). Tag 3 is an arc (center, radius, start and end: seven slots); tag 4 is an elliptical arc (center, major, minor, start and end: ten slots). Tag 5 contains eight coordinates per cubic of a composite spline. The flag is clockwise for arcs, closed for splines, and zero otherwise. The decoder checks tags, integral headers, record lengths, finite coordinates and nonnegative radii before constructing geometry.

The result is `[regionCount, ...regions]`, with each region `[area, ringCount, ...rings]`; the first ring is its outer boundary and the rest are its direct child holes. Each ring contains `[pointCount, ...[x,y], commandSlots, ...commands]`. Numeric commands are `0,x,y` (move), `1,x,y` (line), `2,c1x,c1y,c2x,c2y,x,y` (cubic), `3,rx,ry,rotationDegrees,largeArc,sweep,x,y` (arc), and `4` (close). Coordinates are world-space; arc flags and rotation already encode the SVG convention. JavaScript only changes the sign of Y and formats numbers to five decimal places. Result counts, finite values, command boundaries, flags and closure are validated before exposure to the model.

`kernelRegions.json` captures 120 pre-native arrangements and identifies the unchanged reference source with SHA-256. They cover segments, circles, ellipses, both arc types, composite/closed splines, tangencies, coincident geometry, dangling edges, nested holes, negative-half quantization and imported problem contours. Tests compare face order, vertex order, hole structure, areas and SVG command structure/coordinates; numeric coordinates use 1e-7 absolute plus 1e-10 relative tolerance, with one final 1e-5 SVG formatting unit allowed. Twenty-four dragged benchmark states also compare against the reference, and a binding spy verifies one native region call with no JS intersection/spline callbacks. The full editor suite exercises the routed region API, including export, rendering and hit testing.

Next, reduce costs identified in these measurements and migrate higher-level editing computations where they justify native batching. Document state should move to Rust only after mutation operations have an explicit command/patch contract. Small scalar operations can cost more at the boundary even when larger projections benefit from native loops.

## Trim and extend queries

`GeometryKernel.editing` runs three geometry-only queries in Rust: parameterized curve intersections, trim interval selection, and extension endpoint/target selection. The public `getCurveIntersections`, `getTrimCandidate` and `findExtendCandidate` preserve their signatures and reconstruct original curve references, cutter IDs/types, Vec2 instances and preview data. `trimReference.ts` and `extendReference.ts` retain the pre-routing calculations for the TypeScript fallback. `executeTrim`, `executeExtend`, constraint transfer, document ownership, transactions and undo/redo remain in TypeScript; their mutation code is unchanged.

`curve_editing(curves, settings)` reuses the region curve record format. The first record is the target; the rest are candidate cutters. Settings are `[mode, cursorX, cursorY, controlSpline]`, with mode 0 for intersections, 1 for trim and 2 for extend. The adapter excludes the target identity and preserves the old reserved synthetic extension identities (`__extend_ray__`, `__extend_circle__`, `__extend_ellipse__`). Returned cutter indices are mapped back to the original input array, including duplicate cutters and stable tie precedence.

Mode 0 returns `[count, ...[x,y,param,cutterIndex]]`. Mode 1 returns `[paramA,paramB,startX,startY,endX,endY,startCutter,endCutter,wholeEntity]`. Mode 2 returns `[0]` for no candidate or `[1,endFlag,fromX,fromY,toX,toY,cutterIndex,fullLoop]`. Missing cutters use -1. Record shapes, finite values, flags, parameter domains and source indices are checked before candidates reach the document. Invalid native results propagate without silently executing a second algorithm.

The port retains endpoint exclusion at 1e-4, stable parameter sorting, all-retained-point deduplication, open and cyclic trim intervals, whole-entity removal for closed curves with fewer than two cuts, and the closed control-spline distinction. Extension retains nearest-end ties, the 50,000-unit search ray, 50-unit fallback, degenerate direction fallback, angular guards and full-circle/ellipse conversion. Circular and elliptical extension use the original world-coordinate angles; trim parameters retain their SVG-angle convention. Geometry helpers are shared with native region construction, while extension's world-space ellipse parameterization intentionally retains its unclamped legacy radii.

`kernelEditing.json` captures 256 scenes with four cursor probes each and SHA-256 hashes of both reference modules. Tests compare sorted cuts, interval endpoints, cutter metadata, extension edges/targets and previews. Additional tests cover off-curve cursors, boundary validation, one-call native routing without JS intersection/spline callbacks, and document constraint preservation with undo/redo. Coordinates and parameters use 1e-8 absolute plus 1e-10 relative tolerance; object key order is irrelevant, while geometric array order and cutter precedence are preserved.

The [editing query benchmark](../benchmarks/results/editing.md) measures these queries separately from solver, curve collection, document changes and rendering. Run it with `npm run bench:editing` after building the kernel.

## Fillet geometry

`GeometryKernel.fillet` moves fillet evaluation, extended-curve projection, tangent-circle construction and maximum-radius search into Rust. Supported inputs are segments, circular arcs and fit/control splines represented as cubic segments. Each fillet or maximum-radius query crosses the WASM boundary once; iteration, continuation in radius, reversed curve order and binary search stay native. Preview and commit consume the same result. Connectivity discovery, endpoint IDs, constraint remapping, document mutation and undo/redo remain in TypeScript.

The original numerical implementation is retained in `src/math/filletReference.ts`, with spline calculations imported directly from `splineReference.ts`. The TS fallback calls it without packing. Unsupported curve types keep their previous reference behavior; a failure from a native query propagates. `kernelFillet.json` captures 102 pre-routing fillet/radius queries and 80 evaluation/projection probes. Tests compare both backends to these snapshots, check 120 deterministic transformed curve pairs with actual WASM, and exercise existing fillet constraints, pattern links and history.

API 13 adds `fillet_geometry(curves, settings)` using the existing variable-size region curve records. Settings are `[mode, a, b, hasCorner, cornerX, cornerY, click1X, click1Y, click2X, click2Y]`. Modes are 0 evaluation (`a=t`), 1 projection (`a=x,b=y`), 2 fillet (`a=radius`), and 3 maximum radius (`a=max,b=min`). Evaluation returns `[pointX, pointY, tangentX, tangentY, normalX, normalY]`; projection returns `[t, pointX, pointY, distance]`. Fillets return `[1, centerX, centerY, radius, t1X, t1Y, t2X, t2Y, clockwise, cornerX, cornerY, midX, midY, bisectorX, bisectorY, param1, param2]` or `[0]` when infeasible. Radius search returns `[1, radius]` or `[0]`. Inputs and result layouts are validated; empty-spline projection preserves its infinite-distance sentinel. Public wrappers preserve `Vec2` results, endpoint IDs and borrowed corner/degenerate-point identity.

The port retains the reference's 24 Newton iterations, 1e-3 signed-distance tolerance, radius continuation in steps of at most five, spline-endpoint branch guards, ten binary-search iterations and tenth-unit radius rounding. Arc evaluation still clamps to its span, including the existing unit-X tangent at its final endpoint; spline extensions retain the existing 100-unit parameter scale. This stage preserves those conventions rather than changing fillet behavior. Rebuild generated WASM assets after updating to API 13.

Fillet offset sides at a shared endpoint are anchored to its local curve normals, rather than to the initial radius guess. This prevents a turning spline from selecting the exterior side of an acute arc/spline corner (the Point-94 regression). Disjoint curves retain the seed-based side selection. The recorded 102-query results remain unchanged; the reference source hash includes this correction.

Multiple fillet previews are committed in one deferred solve and one history transaction. When two previews use opposite ends of the same spline, the document extracts the retained interval once from the original cubics and attaches both fillet arcs to its final handles. Overlapping bounds reject the batch before mutation. Numeric queries and preview results still use the selected kernel.

Fillet previews shorten visible arcs and fit/control spline paths at the same endpoint selections used by commit. Spline previews extract a single retained cubic interval for cuts at both ends, and preserve linear endpoint-extension behavior. Original hit paths remain selectable; preview rendering changes neither document geometry nor history, and cancellation restores the original paths.

## Chamfer geometry

`GeometryKernel.chamfer` prepares a corner from its vertex and two far endpoints, then calculates equal-distance, two-distance and distance/angle chamfers in Rust. Each preparation or calculation is one WASM call. Connectivity discovery, primitive IDs, constraints, document mutations, preview formatting and history remain in TypeScript. The direct TS fallback is retained in `src/math/chamferReference.ts`; both paths return the existing `Vec2`-based public results and error messages. The two-distance commit path assigns dimension expressions to the flipped sides, so parameter recomputation and undo/redo preserve the geometry shown in the preview.

API 14 adds `chamfer_geometry(geometry, settings)`. Settings are `[operation, mode, distance1, distance2, angleDegrees, flip]`, with mode 0 equal distance, 1 two distances and 2 distance/angle. Operation 0 accepts `[vertexX, vertexY, other1X, other1Y, other2X, other2Y]` and returns `[1, dir1X, dir1Y, dir2X, dir2Y, len1, len2, cornerAngleRadians]` or `[0]` for a rejected corner. ## Offset geometry

`GeometryKernel.offset` calculates both requested offset sides and the gizmo geometry in one native query after source-curve collection. Rust samples curves, determines closed-chain orientation and outward normals, offsets lines/arcs/circles and sampled splines/ellipses, joins neighbors, and builds fit handles. Spline offsets additionally use analytic source tangents and trim local self-intersection loops before interpolation. Selection, chain connectivity and document mutation stay in TypeScript. `src/math/offsetReference.ts` preserves the pre-native arithmetic; the TypeScript fallback adds matching spline cleanup from `src/math/offsetSpline.ts`. Input and output coordinates are world-space, and public results still contain `Vec2` instances.

API 15 adds `offset_geometry(curves, items, settings)`. Curves use the existing region records. Each item is `[curveIndexOrMinusOne, kind, reversalBits, gizmoClockwise]`; kinds 0–5 are line, arc, spline, circle, ellipse and elliptical arc. Reversal bit 1 reverses spline samples and bit 2 reverses endpoint tangents. Keeping them separate retains the legacy endpoint-orientation metadata used during initial preparation; refined closed splines use consistent tangents at the seam. Arc records already contain ordered chain endpoints and the effective sampling direction; the original clockwise flag is retained separately for the gizmo calculation. Missing geometry uses index -1. Settings are `[closed, referenceItem, direction, distance1, distance2, flip]`, with direction 0 one side, 1 two sides and 2 symmetric; an empty chain uses reference -1.

Results begin `[error, anchorX, anchorY, normalX, normalY, sideCount]`. Every side adds `[error, signedSide, distance, primitiveCount]`. In API 19, each primitive is `[sourceItemIndex, contourIndex, tag, payloadSlots, ...payload]`; earlier versions omitted `contourIndex`. Primitive tags are 0 line (four endpoint coordinates), 1 arc (center, start, end, radius, clockwise), 2 circle (center and radius) and 3 spline. Spline payloads start `[pointCount, closed, hasBasis, hasTangents, hasHandles]`, then contain points, optional bases/normals (two arrays), endpoint tangents and handle pairs. Error codes are 0 valid, 1 missing geometry without a message, 2 collapsed circle radius, 3 collapsed arc radius and 4 empty selection. Invalid sides preserve the original signed-distance metadata; valid sides report an absolute distance. Numeric source indices are mapped back to document IDs in TypeScript. Record sizes, counts, source indices, kinds, flags and finite values are checked on the boundary.

Single ellipses retain 24 offset samples, spline gizmos 64, closed-chain area four and inside/outside tests 16. Splines use 128 samples per Bezier span (up to 4096); elliptical arcs use 512 samples and 65 fit points. Both use analytic normals and local loop removal. All parallel curves are built before their joins: sampled/sampled neighbors are cropped together at their closest local intersection, and sampled/arc or sampled/line neighbors use finite curve intersections. Circle intersections are solved analytically so arc endpoints remain on their radius. When curves diverge, straight tangent extensions meet at a bounded miter, keeping the original parallel endpoints as anchors rather than dragging them to the join. Visible runs are fitted adaptively to compact cubic Beziers with a 0.05 world-unit tolerance. Least-squares fitting uses the source endpoint tangents, monotone Newton parameter refinement, recursive splitting and checked merging of adjacent pieces. Each restricted cubic is compared with a straight cubic on its reference chord; the convex-hull bound controls deviation in both directions, including between input samples. Straight runs have a separate capsule bound. Protected cut and miter corners remain exact with zero handles; closed splines keep quarter boundaries and a shared seam so small loops cannot collapse to a line. Fit-point counts follow geometric complexity rather than a fixed per-span budget. Sampled joins search within eight offset distances of each endpoint; near parallel cases fall back to a bevel. Pure line/arc queries retain their original 1e-7 line-intersection cutoff, radius floor and other primitive fallbacks. The snapshot fixture records 486 pre-port queries across 27 scenes. Repeated side results are stored once without changing captured coordinates; unchanged primitive families still match these snapshots, while spline and elliptical-arc results compare native arithmetic with the corrected TypeScript fallback.
